# 已确认的工具缺陷与假阴性

本文件记录**工具自身**的问题：报了错、报成「没有」、或语义容易误读的行为。ROM 结论、补丁方案、游戏相关地址一律不写在这里——那些属于任务账本。

每条都给出可复现的判据与绕行规则。缺陷未修之前，绕行规则是强制项；修掉之后把状态改成「已修」并保留证据。

## 判据与分级

| 字段 | 含义 |
|------|------|
| 编号 | `TI-nnn`，稳定编号，不复用 |
| 症状 | 调用方直接看到的现象 |
| 证据 | 可复现的命令或调用序列；标 `实锤` / `推测` |
| 影响 | 会让人做出什么错误决定 |
| 状态 | 未修 / 已修 / 已撤（误判） / 上游（不在本仓库） |
| 验证 | 修掉之后可复跑的判据；未修时留空 |
| 绕行 | 修掉之前必须怎么做 |

**假阴性比报错更危险**：报错会让人换路，报「没有」会让人据此排除整类方案。

## TI-001 `sourcegen xref` 只扫描分类为指令的字节，未分类区域整段不可见

| 字段 | 内容 |
|------|------|
| 症状 | 查某个 RAM 地址的写入者时返回 0 条命中，但该地址确实被写 |
| 证据 | 实锤（修复前）：`sourcegen xref --address <addr> --all-banks --writes-only` 报 0 条；同一 ROM 的扁平 PRG 搜出 12 处存储（`8D` 1 处、`8C` 1 处、`9D` 9 处、`99` 1 处）；同一批 bank 的 `stats` 显示该 bank 仅 237 字节被分类为代码（共 16384），另 16303 字节未访问。根因是 `xref` 用 `attrib.IsInstruction` 过滤，分类不到的字节整段跳过 |
| 影响 | 调用方据此判定「没有现成写入者 / 没有现成门控」，转而自造代码洞、计时器或钩子；实际现成机制就在 ROM 里，只需改一个立即数 |
| 状态 | 已修：`tools/SourceGenCli` 的 `xref` 改为逐字节解码，命中带 `tier`（`code`/`raw`）与 `region`（`code`/`data`/`unvisited`），`--code-only` 保留旧语义 |
| 验证 | 同一 ROM、同一地址、同一命令：修复前 0 条，修复后 12 条，与扁平搜逐条对齐（`tests/sourcegen.test.mjs` 用 `BRK` 截断的切片固定住「未分类存储必须命中」这条判据） |
| 绕行 | 无（已修）。旧绕行「再用扁平 PRG 搜 `8D/8C/8E/9D/99/95/94/96/97`」只在需要独立复核某次命中时才有意义 |

## TI-002 「xref 不匹配索引寻址」是误判，同一现象只有一个根因

| 字段 | 内容 |
|------|------|
| 症状 | 原判为 `$xxxx,X` / `$xxxx,Y` 形式不参与地址匹配 |
| 证据 | 实锤（反证）：`OperandTarget` 一直覆盖 `AbsIndexX`/`AbsIndexY`/`DPIndexX`/`DPIndexY`；对同一 bank 用 `--entry <已知 pc>` 补种子后，同一条 `STY $xxxx`（绝对、非索引）立刻出现在结果里。说明缺失的是「分类」而不是「地址模式」——索引与非索引一起缺席 |
| 影响 | 误判会把排查引向地址模式表，而真正的开关在分类过滤上；按错误根因「修」地址模式表得不到任何变化 |
| 状态 | 已撤（误判）。根因并入 TI-001 |
| 验证 | 修复后索引命中与绝对命中同批返回，`mode` 与 `indexed` 逐条正确（同一测试文件覆盖 `Abs`/`AbsIndexX`/`AbsIndexY` 三种模式） |
| 绕行 | 无。教训：一条「某类寻址查不到」的判断，必须先用单条已知指令做对照，确认缺席的是这一类还是全部 |

## TI-003 `sourcegen xref` 的措辞把「未检出」说成「没有」

| 字段 | 内容 |
|------|------|
| 症状 | 输出 `[warn] no reference — 该地址在这些 bank 里没有匹配的绝对/零页操作数` |
| 证据 | 实锤：同一输出在 TI-001 的场景里出现 |
| 影响 | 措辞是断言式的，调用方（尤其自动化流程）会把它当结论而非「本次查询未覆盖到的指令族」 |
| 状态 | 已修：标签改为 `no match`，正文写明「未检出……间接寻址、指针表与计算出的基址不在扫描范围内，不等于该地址没人写」；同时打印扫描字节数与分类指令数，让「扫了多少」和「命中多少」分开 |
| 验证 | 修复后对同一地址取 0 条时输出上述措辞；`tests/sourcegen.test.mjs` 的负例（`JMP` 操作数里的伪存储）走这条分支 |
| 绕行 | 无（已修）。写结论时仍只能用「未检出」 |

## TI-004 `cheat encode` 不校验 compare 的唯一性

| 字段 | 内容 |
|------|------|
| 症状 | 生成 8 位码时只做编解码，不提示该 compare 值在别的 PRG bank 是否也成立 |
| 证据 | 实锤：`cheat encode` 输出码与解码结果，不含逐 bank 字节；唯一性要靠另一条 `cheat check` |
| 影响 | 可切换窗口（`$8000-$BFFF`）的码缺唯一性时，会同时改坏其它 bank 的同偏移代码；这类错误在运行时表现为随机的异常行为，很难回溯到码 |
| 状态 | 未修 |
| 绕行 | 任何落在 `$8000-$BFFF` 的码，交付前必须跑一次 `cheat check --address <cpu>` 并把逐 bank 表贴进交付；唯一性不成立就不要用 8 位码 |

## TI-005 `patch --edit` 默认 bank 0，固定 bank 改动报不出 CPU 地址

| 字段 | 内容 |
|------|------|
| 症状 | 编辑落在 `$C000-$FFFF` 的固定 bank 时，报告里每条编辑都写 `CPU n/a (outside the selected bank)` |
| 证据 | 实锤：默认 `--bank 0`，编辑偏移超出 bank 0 覆盖范围时退回 `null` |
| 影响 | 交付表缺 CPU 地址，读的人无法把「文件偏移」和「调试器里看到的地址」对上；也掩盖了「改动是否落在固定 bank」这个安全判断 |
| 状态 | 未修 |
| 绕行 | 报告 CPU 地址时显式给 `--bank <固定 bank 序号> --bank-cpu-start 0xC000`，或交付表里手工补一列并注明推导方式 |

## TI-006 `load_state` 之后断点是否仍然有效没有确定行为

| 字段 | 内容 |
|------|------|
| 症状 | 读档后先前设好的断点可能不再命中；重新设一次就恢复 |
| 证据 | 推测：观察到「读档前设断点不命中、读档后重设即命中」，未做对照实验确认是读档清空还是别的状态重置 |
| 影响 | 会把「断点没命中」误判成「这段代码没执行」，从而排除正确路径 |
| 状态 | 未修（上游行为未确认） |
| 绕行 | 一律「先读档、后下断点」；断点没命中时先重设一次再下结论 |

## TI-007 `run_frames` 的 `resumed_from` 与 `stopped_by_breakpoint` 语义不同向

| 字段 | 内容 |
|------|------|
| 症状 | 返回 `stopped_by_breakpoint: false` 同时带 `resumed_from: "Breakpoint"` |
| 证据 | 实锤：本次会话多次出现 |
| 影响 | 只看 `stopped_by_breakpoint` 会把「从上次断点恢复后跑满」误读成「没有断点参与」；只看 `resumed_from` 会把「跑满帧数」误读成「命中了断点」 |
| 状态 | 已在本仓库的记录里澄清（字段含义写进工具手册），行为本身不变 |
| 绕行 | 判「本次命中」只看 `stopped_by_breakpoint` 且 `frames_elapsed < frames_requested`；`resumed_from` 只说明起点 |

## TI-008 客户端附件层拒收字节完全相同的截图

| 字段 | 内容 |
|------|------|
| 症状 | 连续两次取帧且画面未变时，图片结果被替换成 `durable image storage rejected the result` |
| 证据 | 实锤：同一帧重复取图即拒绝；推进若干帧或按住按键后再取即可 |
| 影响 | 会以为取图工具坏了，进而改用文本渲染代替截图——那会丢掉几何信息（楼梯、地形） |
| 状态 | 上游（客户端侧，不在本仓库工具内） |
| 绕行 | 两次取图之间必须改变画面；需要同一画面多次分析时，先按键或推帧再取 |

## TI-009 零页地址的 `xref` 结果混有「指向该槽位的指针」命中

| 字段 | 内容 |
|------|------|
| 症状 | 对一个零页地址跑 `--writes-only`，返回条数远多于该地址被直接写的次数，其中多条是 `DPIndIndexY` 之类的间接模式 |
| 证据 | 实锤：同一零页地址返回 23 条，其中 15 条是 `DPIndIndexY`（`LDA ($nn),Y` 一类的读改写变体），报的是「从这个槽位取指针」，不是「写这个槽位」 |
| 影响 | 把指针命中当成对该字节的写入，会得出「这个槽位被十几处代码同时改」的错误结论 |
| 状态 | 已修（输出层）：命中新增 `indirect` 字段，间接模式（`AbsInd` / `DPInd` / `DPIndIndexY` / `DPIndexXInd` / `AbsIndexXInd`）为 `true`，且 `mode` 已能区分；「报不报」的行为不变 |
| 验证 | 同一地址修复后可直接按 `indirect === false` 分出直接写入；`tests/sourcegen.test.mjs` 断言直接命中的 `indirect` 为 `false` |
| 绕行 | 读 `xref` 结果先按 `indirect` 分组；间接命中只用来找指针表，不用来数写入点 |

## 记录规则

- 新增条目：先有可复现判据，再写影响；没有判据的只写「推测」。
- 修掉之后：状态改「已修」，把验证命令留在「验证」列，不要删条目。
- 判错的条目：状态改「已撤（误判）」，在证据列写反证，并注明根因并入哪一条。删掉它等于让下一个人重复同一个误判。
- 上游问题：状态写「上游」，绕行照旧有效。
- 不写游戏名、ROM 名、具体 RAM 地址与存档路径；用 `<addr>`、`<状态字段>` 之类的占位符。
