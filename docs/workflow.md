# NES/6502 ROM 逆向与永久补丁

本文是 NES 逆向工作流的完整规则。工具仓路径全部是仓库相对路径：静态侧是 `third_party/6502bench`（SourceGen），动态侧是 `third_party/MesenGM`（Mesen 与 MCP 调试桥 `MCPServer.exe`），两者由本仓库的 submodule 提供，pin 见 `third_party/pins.json`。

环境未就绪前不要下 ROM 行为结论：先按 [installation](installation.md) 完成构建与注册，再用 `node scripts/verify.mjs` 拿到「桥已应答」的证据。

## 适用边界

- 适用于 NES/6502 及其常见 mapper 的 ROM 逆向、金手指、永久补丁。
- 适用于"把某个动作改成固定效果""让某个数值始终最大""移除/恢复某个判定"这类可观察、可断点验证的目标。
- 不适用于没有可运行模拟器或调试器的纯静态猜测。缺少动态证据时，结论只能标为"推测"或"猜测"。
- 目标效果涉及共享数据表、初始化流程或 AI 时，优先做窄路径代码钩子，不直接改全局表。
- 工具基线：`third_party/6502bench` 负责静态反汇编与符号，`third_party/MesenGM` 的 MCP 调试桥负责动态取证。两者都缺失时只能产出静态推测，不得声称补丁已验证。
- 准入优先于进度：调试桥未生效、静态反汇编参考工程未就绪时，停在环境确认阶段。此时最容易犯的错是用临时脚本去模拟缺失的工具，产出无法复核的证据。

## 核心原则

- 工具先于判断：先把调试桥接入并核验通过，再从参考工程确认反汇编工具的用法，最后才看 ROM。顺序反了，后面每一步都要返工。
- 原始 ROM 只读：先复制、先算哈希，永久补丁另存文件，绝不覆盖原 ROM。`scripts/patch-rom.mjs` 在同一次运行里校验原字节、写新文件、读回并给出前后 SHA256。
- 先动态定位，再静态解释：先用读写断点找到真实写入点和调用路径，再回反汇编确认语义。
- 冷启动是验收基线：即时存档只用于导航和加速，不能单独证明补丁有效。
- 最小改动：只改目标路径。共享表、全局读取覆盖、初始化变量是高风险区。
- 状态正确优先于画面正确：屏幕出现效果不等于实体状态、AI 路径和后续流程没有被破坏。
- 证据分三态：`实锤`（已运行/有结果支撑）、`推测`（已检查未运行）、`猜测`（无证据）。交付中逐条标注。
- 对照优先：出现异常行为时，先用同一存档把补丁/金手指关掉跑同样帧数。关掉就正常，才说明是补丁造成的；关掉也异常，问题在存档、输入或游戏本身。
- 写入者优先：状态值的跳变要找到实际写入指令，不能用"看起来应该"推断。状态可能被看似无关的例程（着陆、动作收尾、初始化）悄悄重写，观察到的时序和真实控制点常常不是同一处。
- 金手指是 CPU 地址覆盖，不是文件补丁：落在可切换区的码会同时命中所有 bank 的同一偏移。

## 工具基线

外部工具仓只用仓库相对路径引用；pin、许可与更新流程见 [third-party](third-party.md)。

| 工具 | 什么时候去查 | 查哪里 |
|------|-------------|--------|
| `third_party/MesenGM` | 需要工具名/参数/上限/返回字段、内存区标识、地址映射口径、断点与存档行为时 | `MCP_SERVER.md`、`MCPServer/skills/mesengm-mcp/references/tool-details.md`、`Core/NES/BaseMapper.cpp` |
| `third_party/6502bench` | 需要静态分析操作、交叉引用、符号与代码生成用法时 | `docs/sgmanual/`（`analysis.html`、`codegen.html`、`advanced.html`） |

取用规则：

- 本文件只写工作流规则，不复述工具仓里的工具细节；细节按上表现查。
- 工具行为以工具仓的源码/手册为准；聊天记忆、旧截图和旧版工具描述只作召回线索。
- 读不到工具仓时，按「调试器操作锚点」的通用语义降级执行，并在交付「未决」里标注工具面未核实。
- 参考工程只提供工具事实，不提供目标 ROM 的事实；ROM 结论必须来自本 ROM 的动态取证。
- 客户端接入、注册与生效核验见 [installation](installation.md)；工具面没出现时，不要用手写脚本绕开注册去凑证据。
- 反汇编输出出现大段 `unidentified`、字节块或明显断裂时，先当成工具的分析缓存问题处理：确认不是缺少分析入口/代码标记，再考虑换工具或重建工程。不要在手写反汇编器上继续推进，那会把工具缺陷变成结论缺陷。
- 金手指的解码/编码规则以 `third_party/MesenGM` 的 `CheatManager` 实现为准（`Core/Shared/CheatManager.cpp`）；第三方编码器的位序、校验位约定经常不同，交付前必须用同一份实现反解校验。`scripts/cheat-code.mjs` 就是这套位序的可执行副本。

## 工作流

### 环境就绪（setup）

先构建或定位两个工具，再注册并核验调试桥：

1. `node scripts/setup.mjs` 检查构建先决、构建 MesenGM 与 6502bench，并写出客户端注册条目到 `out/`。
2. 把 `out/client-setup.md` 里的条目加进 MCP 客户端。
3. `node scripts/rea-fc.mjs emulator provision --rom <rom>` 让模拟器可启动、手柄端口可用；判定细节见 [emulator-init](emulator-init.md)。
4. `node scripts/verify.mjs` 证明工具面存在：桥应答 `initialize` 与 `tools/list`，模拟器层与输入端口通过，`get_rom_info` 返回目标 ROM。

注册成功不等于已生效，只有 `get_rom_info` 给出目标 ROM 才算接入完成。此步失败时不进入动态取证，按缺失处理，结论上限为「推测」。

桥的握手只覆盖桥：它能应答、乃至报出完整工具面，而模拟器本身可能起不来、载不进 ROM 或收不到按键。这三件事分别由 profile 目录、`settings.json` 与手柄端口决定，判据与补齐步骤见 [emulator-init](emulator-init.md)。先用 `node scripts/rea-fc.mjs doctor --live` 看模拟器层与输入端口层是否通过，再开始取证。

静态侧同样是门槛：先确认 `third_party/6502bench` 能打开目标 ROM、能导出汇编、能做字节环回，再开始解释机器码。参考工程不可用时，不要手写反汇编器、解析器或内存扫描器去顶替它。

两条门槛都通过之前，只做只读的环境确认，不下任何 ROM 行为结论，也不用脚本绕行。绕行的代价是后续所有证据都无法复核，而且返工要重来一遍。

### 固定基线与回滚点

- 读取 iNES 头：PRG/CHR 大小、mapper、镜像方式。`node scripts/rea-fc.mjs info <rom>` 直接给出这些字段与 SHA256。
- 计算并记录原 ROM 的 SHA256、文件大小。
- 复制原 ROM 到只读基线位置；补丁写入新文件。
- 把目标改写成"可验证的断言"，例如：
  - 目标动作触发时，某个状态变量在指定写入点被写为确定值；
  - 下游处理器读取的效果值达到预期；
  - 持续时间/计时器落在可测量的帧数范围内。
- 不要写"效果变强"这类无法验收的描述。断言必须包含变量、写入点、值和观测方式。

### 静态定位

- 用 `third_party/6502bench` 建立可复现的反汇编工程：CPU 选型、入口点、分析范围按该工程手册操作，不在会话里手工拼反汇编。
- 无人值守时用 `node scripts/rea-fc.mjs sourcegen`：它把 PRG bank 切出来交给 `tools/SourceGenCli`（用 pin 的 `DisasmProject`/`CpuDef`/`Am65` 分析，不是自写反汇编器），给出覆盖率、按地址列指令、按操作数查引用，还能把结果存成 `.dis65` 供界面继续加工。
- `SourceGen.exe` 只接受一个参数，且必须是已有的 `.dis65` 工程（`MainController.ProcessCommandLine` → `DoOpenFile` 走工程反序列化）：没有 headless 模式，也没有导出开关。从 ROM 建工程、交叉引用与导出汇编在界面里做；命令行侧用上面的驱动器，或在没有驱动器时退回调试桥的 `get_disassembly` 并在交付里注明「无符号、无交叉引用」，结论上限随之下调。
- 反汇编目标 PRG bank，建立例程、数据表、RAM 变量的符号；符号命名要能直接用于补丁脚本和调试断点。
- 对候选变量做交叉引用：优先用工程的引用视图，手写搜索结果只作补充；找出所有读取者、写入者、初始化者和每帧更新者。
- 分析结果先导出一份汇编源码做字节环回校验（装配后与原 PRG 逐字节比对），环回不一致说明代码/数据边界划分有误。
- 区分三类位置：
  - 初始化时写入：改它可能影响开局状态；
  - 每帧/持续状态时写入：改它可能影响移动、碰撞、AI；
  - 目标动作瞬间写入：通常是代码钩子的最佳落点。
- 如果一张表同时被初始化、AI 和玩家路径读取，不要全局改表；先找只属于目标动作的窄例程。
- 记录候选例程的入口、分支、调用者和返回路径。

### 动态验证

- 加载原 ROM，手动走到目标场景；即时存档只用于减少重复导航。
- 先确认调试桥的内存区标识，再按标识区分 PRG ROM 与内部 RAM；不要把两者混用。
- 在目标变量上设写断点，记录每次命中的 `PC`、`A/X/Y`、旧值和新值。断点接口可能是整体替换而非追加，设置前先确认当前列表。
- 取证一律走客户端托管的常驻 MCP 会话，不要用「每次调用拉起一个桥进程」的批处理客户端做逐帧轮询：常驻会话复用同一次握手，批处理客户端每次都要重新启动并握手。判据是客户端工具面里能看到带服务器前缀的桥工具；只有脚本能读、客户端里看不到，说明注册没生效。
- 在候选例程上设执行断点，确认实际走的是哪条分支，而不是只看最终画面。
- 断点命中后的寄存器、执行轨迹、调试事件取证走调试桥接口；它的反汇编只做就近指令边界核对，不替代静态分析。
- 写断点能设、但事件列表恒为空（`get_debug_events` 计数为 0、`get_trace_tail` 无行）时，写入者取证改走这条路径：已知变量地址 → 用 `sourcegen xref --all-banks --writes-only` 按操作数找候选指令（或退回扁平 PRG 搜 `8D/9D/99 <lo> <hi>`）→ 命中地址还原成 CPU 地址与文件偏移 → 读上下文确认归属。跨 bank 的命中先用 `$8000-$BFFF` 的字节串与各 bank 逐一比对确定当前映射，再换算地址；不要把「值变化的帧号」当成写入指令的位置。
- `sourcegen` 的覆盖率是判断分析是否到位的判据：某个 bank 只有个位数指令说明种子入口没落在代码上，用 `--entry` 补入口点或换 bank 起点，不要拿低覆盖率的引用列表下结论。
- 断点或轨迹接口返回空、命中数恒为 0 时，不要停下来等修工具：改用帧轮询降级取证。每次推进一帧，读一组变量，按"值变化的那一帧"定位动作，记录帧号与前后值；交付时注明这是轮询证据，不是断点证据。
- 轮询要读前后两帧再下结论。一次单帧采样很容易把相邻帧完成的多个状态转移当成一个状态，从而误判状态机的转移条件。
- 解释 `$8000-$BFFF` 的字节前先确认当前 bank。该窗口的映射可能逐帧切换；取一段足够长的字节串，与各 PRG bank 的同区间逐一比对，确定当前映射后，再把这个 CPU 地址换算成 bank 内偏移。混用 bank 会把 A 例程的机器码当成 B 例程解释。
- 按字节搜代码或查交叉引用时，注意内存区的地址口径：CPU/内存视图只覆盖当前映射，跨 bank 的搜索要到扁平 PRG ROM 镜像里做，再用 bank 比对把命中还原成 CPU 地址。
- 直接改 PRG 内存只对当前进程有效；重新载入 ROM 会丢掉这些改动。做 A/B 之前重新写入并读回确认，不要把"载入后行为恢复原样"误判成补丁无效。
- 即时存档可能停在事件中途（伤害结算、状态切换）。读档后先快照一组关键变量，再判断"读档后立刻发生的异常"是存档本身带来的，还是补丁造成的；不要假定存档是静止的干净起点。
- 读不到预期值时先确认工具调用本身成功，再怀疑补丁。
- 如果读到的值不是预期值，先查是否还有后写覆盖、另一张表、另一条 AI 或分支路径；不要直接认定补丁没生效。
- 找到控制归属：玩家/CPU、操作对象、实体索引、动作状态。
- 找到"目标动作发生"的稳定判据，例如归属索引、控制标志位、动作计时器。

### 选择补丁形态

按风险从低到高选择：

- **窄路径代码钩子**（最低风险，优先）：在目标动作的稳定指令处跳转到代码洞，写入效果值，再回到原流程。
- **独占数据表修改**：只有目标路径读取该表，且冷启动验证通过时才用。
- **全局表/全局读取覆盖**（最高风险）：只用于探索或显示型数值；不得用于实体状态、初始化变量、弹道或物品状态。

金手指与 ROM 补丁的取舍：

- 永久交付优先 ROM 补丁。
- 金手指适合探索，但全局读取覆盖会同时影响初始化、AI 和其他实体，容易造成"实体不动/角色卡死"。
- 如果必须做金手指，优先能改变 ROM 行为的最小写入，不要对状态变量做持续读取覆盖。
- 同一交付里不要同时提供高风险金手指和 ROM 补丁；用户会混淆加载路径。
- 交付前移除或禁用实验性金手指文件；模拟器可能仍在内存中保留旧 cheats，要求重启后再验收。

### 金手指形态

- 码的构成：短码 6 位是"地址 + 值"，长码 8 位是"地址 + 值 + 校验值"（末两位承担校验）。校验位的语义是条件替换——只有 CPU 读到的当前值等于校验值时，才替换成目标值。
- 校验不匹配时码静默失效，不会报错。表现是"码写了但一点都不生效"，很容易被误判成地址算错。
- 生效机制是"按 CPU 地址拦截读取"，不改 ROM 文件。因此同一个 CPU 地址在任何 bank 映射下都会被同样命中。
- 固定 bank（通常 `$C000-$FFFF`）的码是安全的。可切换窗口（通常 `$8000-$BFFF`）的码会同时替换所有 bank 的同一偏移，必须带校验值。
- 校验值的选法：先 dump 目标偏移在每个 PRG bank 的原始字节，确认只有目标 bank 等于该值。存在第二个 bank 同值时，这条码会连带改坏那段代码；换落点或改回 ROM 补丁，不要赌它不会被执行。`node scripts/rea-fc.mjs cheat check --rom <rom> --address <cpu>` 直接给出这份逐 bank 字节表与唯一性结论。
- 落点优先级：能在固定 bank 完成的改动，不要放到可切换区。等价效果有多个落点时，先选固定 bank 的那个。
- 需要多字节改动时，每条码各自带各自的原值校验；只给其中一条加校验，其余仍然是全局覆盖。
- 同一地址只允许一条码；给同一地址多条码时，只有后应用的那条生效。
- 生效核验必须双读：CPU 视图读到新值、PRG ROM 视图仍读到原值，才算"码生效且 ROM 未变"。CPU 视图仍是原值说明码没加载；PRG 视图也是新值说明改的是 ROM，不是码。
- 清单热加载：金手指清单通常只在载入 ROM 时应用，改完清单要重新载入 ROM 再验，读档不会重新应用。
- 多行码的分隔符要和实现一致。清单用 LF、编辑器按 CRLF 切分时，整段会被当成一条码判为不合法；运行时却可能仍按 LF 正常应用。遇到"运行时有效、编辑器报不合法"先查这条，不要先怀疑码本身。
- 交付内容：码本身、解码后的地址/值/校验、以及"该偏移在各 bank 的原始字节"这份唯一性证据。

### 生成最小补丁

- 用脚本从原 ROM 生成补丁，不用手工十六进制编辑。`node scripts/rea-fc.mjs patch --rom <rom> --out <patched> --edit <offset>:<old>:<new>[:note] [--ips <file>]` 会校验原字节、写入、读回、给出前后 SHA256，并可按需导出 IPS。
- 写入前断言原字节匹配；写入后读回并计算新 SHA256。
- 试验期可以直接写 PRG 内存快速验证效果，但交付物必须来自脚本对原 ROM 的确定性写入；导出的 IPS 只作交付格式，不替代脚本。
- 钩子必须满足：
  - 三字节 `JMP` 落在完整指令边界，不切断原指令；
  - 代码洞位于同一 bank 的连续 `FF` 区域，长度足够并留余量；
  - 不覆盖 bank ID、向量、其他代码或数据；
  - 代码洞保留被替换指令的语义；
  - 分支偏移按新地址重新计算；
  - 返回地址是原指令的下一条指令；
  - 栈平衡，不留下未配对的 `JSR`/`RTS`。
- 如果跳过原调用会跳过必要的状态更新，不要提前 `RTS`；写完值后回到原流程继续。
- 如果目标只是"跳过一段副作用指令"，优先用一个 `JMP` 直接越过这一段，落到后续流程的指令边界上。它比"搬进代码洞再跳回"更小、更不容易出错，但必须逐条确认被跳过的那段没有其他必要副作用。
- 如果目标只是"改一个比较值/常量"，直接改操作数，不要为此挖代码洞。
- 用控制标志做守卫，不要硬编码"玩家 1"或固定实体索引。
- 如果效果由"选择器 + 派生值"组成，两个值都要写；只写选择器可能被后续逻辑覆盖。

### 冷启动验收

按以下顺序验收，前一动作失败不进入下一动作：

- 先做完全重置/冷加载，从标题和主菜单手动进入目标场景。冷启动要用调试桥重新载入原 ROM 或补丁 ROM，不要用旧即时存档代替。
- 接着测"未触发效果"的基础行为：移动、碰撞、拾取/攻击、菜单是否正常。
- 触发目标动作，在补丁写入点设写断点，确认 `PC` 和写入值。
- 继续运行到下游处理器，确认最终效果值与预期一致。
- 检查派生状态是否被后续逻辑复位；瞬时值要在写入点取证，不能只看几帧后的内存。
- 发现异常时先跑对照组：同一检查点、同样输入、同样帧数，补丁关掉再跑一遍。关掉正常才算补丁问题；两边一样异常，先查存档时机、输入残留和游戏本身。
- 从冷启动场景建立检查点，重复 10 次目标动作；记录命中率。检查点用存档读档做 A/B；输入覆盖要显式释放，不会随停机自动解除。
- 做回归：CPU/AI 路径、普通动作、关卡开始/结束、菜单进出。
- 最后再做一次完整冷启动，确认不是检查点掩盖了初始化问题。

只有完成以上步骤，才能把结论标为 `实锤`。

### 交付与回滚

交付必须包含：

- 原 ROM 路径与 SHA256；
- 补丁 ROM 路径与 SHA256；
- 修改表：文件偏移、CPU 地址、原字节、新字节、作用；
- 冷启动验证路径、写入点、写入值、重复次数；
- 基础移动/回归测试结果；
- 回滚方式；
- 未决风险（例如未跑完整流程、只验证了玩家路径、未覆盖其他模式）。

只交付金手指时，替换为：

- 原 ROM 路径与 SHA256（金手指不改文件，SHA256 用于证明 ROM 未被改）；
- 每条码及其解码结果：CPU 地址、目标值、校验值；
- 该偏移在各 PRG bank 的原始字节（证明校验值唯一）；
- CPU 视图与 PRG ROM 视图的双读结果；
- 清单重载与启用步骤；
- 对照组跑的结果（关掉码之后异常不复现）；
- 回归项与未决风险。

## 调试器操作锚点

工具名、参数、上限与返回字段一律以 `third_party/MesenGM` 为准，本文件不复述。需要查的时机：

| 时机 | 去查 |
|------|------|
| 首次连接、确认 ROM 与内存区标识 | `MCP_SERVER.md` 的工具表，配合运行时返回的标识列表 |
| 载入 ROM、套补丁、切换 ROM | `load_rom`/`close_rom`，导出用 `save_rom`，见 `MCP_SERVER.md`；桥不可用时用 Mesen 界面 |
| 读写/搜索内存、下断点、单步推帧 | `MCPServer/skills/mesengm-mcp/references/tool-details.md` |
| 存档读档做 A/B、导出 IPS | `save_state`/`load_state` 做 A/B，`save_rom` 导出，见 `MCP_SERVER.md`；桥不可用时用 Mesen 界面 |
| 确认 PRG 地址是扁平镜像还是 bank 视图 | `Core/NES/BaseMapper.cpp` 的地址映射与 PRG 内存注册处 |

工作流只依赖以下语义，具体工具名自行对号：

- 分别使用 PRG ROM 与内部 RAM 两种内存类型读写；不要把两者混用。
- 写断点用于找"谁写了这个变量"；执行断点用于找"走了哪条例程"。
- 不同调试器的写断点触发时机可能不同；先确认断点是在写入前还是写入后命中，避免把 A 当成写入值或旧值。
- 断点命中后先记录 `PC`、寄存器、目标地址旧值，再决定是否继续。
- 加载即时存档后重新核对 PRG 补丁是否仍在；必要时重新应用并读回。
- 用帧步进/暂停定位动作瞬间；用截图只做辅助，不作为状态证据。
- 冷启动验收使用"重新载入 ROM"，不要用旧存档代替。
- 工具报错先读错误本体；工具失败不等于补丁失效。

NES 文件偏移换算：

- 先确认 PRG 内存区的寻址口径：若是扁平镜像，`file_offset = 0x10 + prg_rom_offset`，不必算 mapper bank；若是 bank 视图，才走下面的 CPU 地址换算。
- 按 CPU 地址换算时：

```text
file_offset = 0x10 + prg_bank_index * prg_bank_size + (cpu_address - bank_cpu_start)
```

- `0x10` 是 iNES 头长度；带 trainer 的 ROM 还要加上 trainer 的 `0x200`（`scripts/patch-rom.mjs` 与 `scripts/lib/rom.mjs` 已按 header 处理）。
- 常见 PRG bank 为 16 KB；以实际 header 和 mapper 为准。
- 映射到 `$8000` 的 bank 用 `$8000` 作 `bank_cpu_start`；映射到 `$C000` 的 bank 用 `$C000`。
- 必须验证 bank 末尾的 bank ID 或 mapper 寄存器；bank 编号不总是线性。
- MMC3 等 mapper 会在运行中切换 bank；同一个 CPU 地址在不同时刻可能对应不同文件偏移。修改前先确认当前 bank，或直接在模拟器的 PRG 内存中按当前映射写入并读回。
- 代码洞不要跨 bank，不要覆盖 bank 末尾的 ID 字节。

## 代码洞与钩子检查表

- [ ] 钩子点确实是目标路径必经之处，且不会被其他路径共享。
- [ ] 三字节 `JMP` 没有切断多字节指令。
- [ ] 代码洞在目标 bank 内，连续 `FF`，长度足够。
- [ ] 代码洞没有覆盖代码、bank ID、向量或数据。
- [ ] 被替换指令在代码洞中按原语义执行。
- [ ] 条件分支偏移按代码洞地址重新计算。
- [ ] 跳回地址是原指令的下一条指令。
- [ ] 玩家/CPU 守卫使用控制标志，不硬编码实体编号。
- [ ] 写入宽度正确，不存在零页回绕或高低字节错位。
- [ ] 下游状态更新没有被提前 `RTS` 跳过。
- [ ] 冷启动 10/10 命中，基础移动与 AI 路径回归通过。
- [ ] 模拟器层通过：`emulator-setup` 与 `input-probe` 都 `ok`，且 `run_frames` 的 `frames_elapsed` 等于请求值。
- [ ] 反汇编来自 `third_party/6502bench` 工程，且导出源码装配后与原 PRG 逐字节一致。没有工程时这一项如实标为未满足，用调试桥的 `get_disassembly` 顶替不能勾选；交付里「未决」要写清哪些结论只靠线性反汇编。
- [ ] 反汇编结论能指出指令的来源：工程导出，或 `get_disassembly` 的地址与 `line_count`；两条都拿不出时，写入者结论不成立。
- [ ] PRG 断点/读写所用的地址口径已按 `third_party/MesenGM` 的地址映射实现确认，不依赖取样时刻的 bank 映射。
- [ ] 金手指落在可切换区时带校验值，且已 dump 该偏移在各 bank 的原始字节确认唯一。
- [ ] 已双读确认：CPU 视图为新值、PRG ROM 视图为原值。
- [ ] 已做"关掉补丁/金手指"的同存档对照跑，异常不复现。
- [ ] 状态跳变已定位到实际写入指令，不是靠观察推断。
- [ ] 金手指清单改动后已重新载入 ROM 再验。

## 症状诊断

| 症状 | 优先怀疑 | 检查动作 |
|------|---------|---------|
| 桥握手绿但一条命令都取不到证据 | 模拟器层或输入端口层没过 | `node scripts/rea-fc.mjs doctor --live`；按 [emulator-init](emulator-init.md) 补齐 |
| 模拟器启动后立刻退出 | profile 目录缺原生库 | 看 stderr 的 `DllNotFoundException` 路径；`node scripts/rea-fc.mjs emulator provision` |
| `set_input` 报「Controller 0 is not available」 | 手柄端口是 `None` | `emulator provision` 后重启模拟器；再用 `clear_input` 的 `available_controllers` 复核 |
| 按键送进去了但画面不动 | `run_frames` 返回 `timed_out` 且 `frames_elapsed` 为 `0`，按键被随后的释放吞掉 | 原样重试同一次推帧，拿到帧数后再释放按键 |
| 实体/弹道在冷启动后不动 | 全局表或读取覆盖改到了初始化/状态变量 | 移除实验性 cheats；冷启动先测不带效果的移动；改用窄路径钩子 |
| 画面有效但状态异常 | 只改了显示值或一次性值 | 在写入点看持久状态和下游处理器；检查是否被后续逻辑复位 |
| 效果不出现 | 走了另一张表或另一条分支 | 在写入点记录实际 `PC` 和值；检查玩家/CPU 守卫与分支路径 |
| 读到的值不是预期值 | 后写覆盖或多路径写入 | 对所有写入设断点，按时间顺序记录；不要只看最终内存 |
| 黑屏/崩溃 | 代码洞覆盖代码、跨 bank、栈不平衡、跳回地址错误 | 核对原字节、bank ID、返回地址和栈；逐条回退补丁定位 |
| 存档有效、冷启动无效 | 初始化路径未覆盖或旧 cheats 残留 | 完整冷启动；重启模拟器；删除旧金手指文件 |
| 只有玩家有效、AI 异常 | 守卫过宽或表被全局修改 | 检查控制标志；让 AI 走原路径；回归 CPU/AI 动作 |
| 工具报错或提示无 ROM | 桥接未连上、ROM 已关闭，或参数用了不存在的内存区 | 先查 `third_party/MesenGM/MCP_SERVER.md` 的工具表确认参数与状态查询接口；重新载入 ROM；不要把工具失败当成补丁失效 |
| 工具调用超时 | 模拟器自身停在调试器或弹出模态窗口 | 先恢复执行并关掉对话框；具体超时上限查 `third_party/MesenGM` |
| 开着补丁时出现与目标无关的异常，关掉就正常 | 金手指落在可切换区且未带校验值，污染了其他 bank | dump 该偏移在每个 bank 的原始字节；换成带校验的码或改落点 |
| 金手指清单改完没反应 | 清单只在载入 ROM 时应用 | 重新载入 ROM；再双读 CPU/PRG 两个视图确认 |
| 断点从不命中，轨迹/事件计数恒为 0 | 调试桥的断点或事件接口不可用 | 不要等工具修复；改用逐帧轮询按值变化定位，并在交付里注明证据类型 |
| 写断点设上了，事件列表仍为空 | 本版本的断点事件通道不可用 | 写入者改走「变量地址 → PRG 搜写操作码 → 还原 CPU 地址 → `get_disassembly`」这条路径；不要用值变化时机代替写入指令 |
| 反汇编只能读到当前映射的那一段 | `get_disassembly` 走 CPU 地址，不覆盖未映射的 bank | 先用 `$8000-$BFFF` 的字节串与各 PRG bank 比对确定映射，再解释；跨 bank 的静态检索一律在扁平 PRG 镜像里做 |
| 反汇编出现大段 `unidentified` 或数据块 | 工具的分析缓存缺少该段结果 | 让工具完整分析/强制反汇编；不要转去手写反汇编器 |
| 同一个 CPU 地址每次取样字节都不一样 | bank 在逐帧切换 | 取一段字节串与各 PRG bank 比对，先确定当前映射再解释 |
| 改了 PRG 内存后行为回退 | 重新载入 ROM 丢掉了内存改动 | A/B 前重新写入并读回；把"载入后恢复原样"和"补丁无效"区分开 |

## 禁止

- 不覆盖原 ROM。
- 不交付未经冷启动验证的全局表补丁。
- 不用即时存档单独证明补丁有效。
- 不把 CPU 地址直接当文件偏移。
- 不覆盖非 `FF` 的"看起来像空闲区"的代码洞。
- 不对实体状态、初始化变量做全局读取覆盖。
- 不在未检查交叉引用的情况下修改共享表。
- 不把屏幕效果当作状态正确的证据。
- 不在可切换区使用不带校验值的金手指码。
- 不把金手指的 CPU 地址当文件偏移。
- 不用"观察到的状态跳变"替代写入者取证。
- 不在补丁开启时把异常归因于游戏或存档，先跑对照组。
- 不在调试桥未生效时用自制脚本、外部内存工具代替取证。
- 不把桥的握手通过当成模拟器可用：模拟器层与输入端口层没过时，结论停在「推测」。
- 不在反汇编参考工程未就绪时手写反汇编器或解析器。
- 不隐藏失败路径或未验证项。

## 反面模式

- 全局修改共享表（动作表、阈值表、角色/单位参数）：冷启动后目标对象不动或行为异常，还会污染其他共用该表的系统。
- 用持续读取覆盖改状态变量：状态被压住，初始化和后续流程都走不到，表现为对象冻结。
- 用一次性写入改瞬时值：写入后立刻被下游逻辑复位，画面看着有效、状态没有持久改变。
- 修正方向一致：把改动收窄到目标动作瞬间的窄路径，保留原初始化、原表和原流程。
